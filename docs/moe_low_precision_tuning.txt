MoE low-precision expert FFN tuning on PPU
========================================

Scope: MoE implementation, its correctness tests, and result documentation.
The existing 20 benchmark parameter sets, registrations, input/output contract,
capacity rules, all seven expert modes, and numerical tolerances are unchanged.
MQA is separately tuned/refactored; see docs/mqa_low_precision_tuning.txt.

Changes
-------
The MoE source grows from 683 to 713 lines (+30) and retains the same six
launchable kernel definitions. No additional runtime kernel is introduced.
Only the up/down expert kernels and their launch parameters are tuned.
The up kernel already fuses the two gated projections and activation; this
fusion and all existing projection/activation rounding boundaries are retained.

One launch-policy helper chooses (M,N,K,pipeline stages) from routed work:
- FP32 or min(C,F)<512: original (16,32,32), default loop pipeline.
- Otherwise, T*K >= 64*E: (128,64,64,3).
- Otherwise, T*K >= 16*E: (64,128,64,3).
- Remaining low-precision model widths: (16,64,64,3).
Here T is flattened token count, K is top_k, E is expert count.
Larger M reuses expert weights over more tokens. Wider N/K tiles improve
memory transfers and matrix-product utilization. Explicit tl.range stage
annotations enable the chosen pipeline in the nested expert GEMM loops.
Forward accumulation remains FP32 and FP32 products use ieee precision.
Expert and route addresses retain int64 for model weights beyond 2**31 elements.
No backend-specific intrinsics, TLE dependency, or PyTorch host compute is added.

Validation
----------
247 correctness tests passed: original 203 plus 44 targeted cases covering
all three tuned tiles, FP16/BF16, gated/non-gated experts, width/token tails,
noncontiguous strides, rank-2/rank-3 inputs, empty experts, and capacity drops.
All 60 dtype/shape paired runs passed against both references (120 comparisons).
All returned routing logits, indices and weights were bitwise identical to
before in all 60 runs. Numerical tolerances remain FP16 0.004, BF16 0.03,
FP32 5e-5 (absolute and relative). Native top-k differences, if present from
near-tie projection rounding, are recorded and checked using returned logits;
native timing always includes its own projection. No timing uses injected logits.

Measurements
------------
PPU-ZW810E; CUDA_VISIBLE_DEVICES isolates one GPU per process;
PPU_FP32_TENSOR_OVERRIDE=0, OMP_NUM_THREADS=4, deterministic shape seeds.
Before/after/padded/grouped run in one process on identical inputs.
Timing: triton.testing.do_bench(warmup=10,rep=50,return_mode="median").
The padded reference computes experts at fixed capacity; the grouped reference
uses native grouped GEMM over retained routes. Both are project benchmark
references, rather than an externally supplied acceptance benchmark.

Geometric mean performance = reference latency / implementation latency.
A mean of 0.8x corresponds to 80% of reference performance.
Statistics below are from the complete original paired run without replacing
any timing with isolated-control remeasurements. Arithmetic means and counts
at or above 0.8x are also included in the accompanying CSV.

Small-control recheck
---------------------
The full benchmark ran while correctness JIT compilation used the other GPU.
Two small cases showed large timing variation. After tests completed, they
were remeasured in five alternating before/after/reference orders, with
warmup=10 ms and rep=100 ms; the medians below are supplemental evidence.
The full-run data above is retained unchanged.
case 5 torch.float16: before=0.085960 ms, after=0.088100 ms, before/after=0.9757x
case 1 torch.float32: before=0.121040 ms, after=0.121020 ms, before/after=1.0002x

Remaining gaps
--------------
A passing mean does not imply every shape reaches 0.8x. Mixtral case 18
remains near 0.78x of the native grouped reference despite roughly 6x
implementation improvement. Several existing FP32 cases remain below 0.8x.
No official acceptance dataset or aggregation rule was supplied. Results
establish the stated mean target on the unchanged local benchmark sets.
MetaX and other backends still require their own correctness/performance runs.

Reproduce
---------

PPU_FP32_TENSOR_OVERRIDE=0 PYTHONPATH=src pytest -q -s benchmark/test_moe_gate_top_k_routing.py --level core --warmup 10 --iter 50 --record json --output moe_tuned.json
